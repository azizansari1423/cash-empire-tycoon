# Phase 1 Architecture — Cash Empire Tycoon (Revised)

**Date:** 2026-11-24 (revised from initial review)
**Scope:** `PlayerDataManager.lua` session locking design
**Status:** Pending implementation approval

---

## 1. Design Principle

The root defect in the initial implementation is a **two-DataStore architecture** where the session lock (`TycoonSessionLocks_v1`) and the player data (`TycoonPlayerData_v1`) are separate keys. Roblox DataStores provide no cross-key atomic operations. Any design that checks the lock in one key and writes data to another cannot guarantee that the lock is still held at the moment the write executes.

**The fix:** embed `_session` directly inside the `TycoonPlayerData_v1` record. Every lock check and data write then occurs inside a single `UpdateAsync` callback on a single key — atomic by construction.

No second DataStore is needed. `TycoonSessionLocks_v1` is removed entirely.

---

## 2. On-Disk Record Format

```
TycoonPlayerData_v1[userId]
─────────────────────────────────────
{
    _session = {
        jobId    : string,   -- game.JobId (or studio fallback) of the owning server
        token    : string,   -- UUID generated by HttpService:GenerateGUID(false)
        since    : number,   -- os.time() when session was last refreshed
        released : boolean,  -- true once session is explicitly released
    },
    Cash               : number,
    TotalEarned        : number,
    PrestigeLevel      : number,
    PrestigeMultiplier : number,
    UnlockedUpgrades   : array,
    StarterPackClaimed : boolean,
    RedeemedCodes      : table,
    GroupBonusClaimed  : boolean,
    Gamepasses         : table,
}
```

**Legacy records** (existing players) have no `_session` field. They are detected by the absence of `result._session` and treated identically to a released session — available for acquisition on first join.

**`_session` is never exposed to game logic.** It is stripped before data is returned to `loadPlayer`'s caller and is never present in the `loadedData[userId]` table. It is restored from the DataStore record inside the `savePlayer` callback.

## 3. Fencing Token

A fencing token is a string value that proves "my server wrote this record last." It allows `savePlayer` to atomically verify session ownership inside the same callback that writes new data.

**Generation:** `HttpService:GenerateGUID(false)` produces a 36-character UUID. It is generated **once per `loadPlayer` invocation**, outside the `UpdateAsync` callback, before the callback is constructed.

```
-- Correct: generated outside the callback
local token = HttpService:GenerateGUID(false)
PlayerStore:UpdateAsync(userId, function(current)
    -- token is captured read-only; never mutated inside the callback
    ...
    newRecord._session = { ..., token = token, ... }
    return newRecord
end)
```

**Association with one player session:** The token is specific to the tuple `(userId, server instance, join event)`. It is stored in `sessionTokens[userId]` only after successful acquisition and is cleared on `PlayerRemoving` or confirmed session loss. If the same player rejoins the same server (unusual but possible), `loadPlayer` generates a new token and `sessionTokens[userId]` is overwritten.

**Why GUID and not `os.time()`:** `os.time()` has 1-second resolution. Two servers starting within the same second for the same player would collide. GUID collision probability is negligible (~10⁻³⁶ per pair).

## 4. Session Acquisition (`loadPlayer`)

### 4.1 Pre-callback state

```
token  ← HttpService:GenerateGUID(false)   -- fixed for this invocation
JOB_ID ← game.JobId or studio fallback     -- module-level constant
```

### 4.2 Callback logic (pure function of `current`)

The callback mutates **no external state**. It reads `token` and `JOB_ID` as read-only captures. Its return value is the sole source of truth for the acquisition result.

```
callback(current):

    now = os.time()

    Case A — another live server holds this session:
        current._session exists
        AND current._session.jobId ≠ JOB_ID
        AND current._session.released ≠ true
        AND (now − current._session.since) < LOCK_TTL
        → return nil                           -- abort; DataStore unchanged

    Case B — acquirable (all other cases):
        • current is nil                       → new player
        • current has no _session              → legacy record
        • current._session.jobId == JOB_ID     → our own stale lock (re-entrancy)
        • current._session.released == true    → explicitly released
        • (now − current._session.since) ≥ LOCK_TTL → expired lock

        → build newRecord:
            copy all fields from current where key ≠ "_session"
            (this is {} for new players, all saved fields for existing/legacy)
            newRecord._session = { jobId=JOB_ID, token=token, since=now, released=false }
            return newRecord
```

### 4.3 Verifying acquisition without closure mutation

After `pcall(UpdateAsync)` returns:

```
ok, result, _keyInfo = pcall(PlayerStore.UpdateAsync, PlayerStore, userId, callback)

if not ok:
    → DataStore error; eligible for retry

if result._session == nil or result._session.token ≠ token:
    if result was nil:
        → callback returned nil (Case A — another server owns the session)
        → kick player; do NOT retry (this is confirmed state, not transient)
    else:
        → unexpected: our UpdateAsync returned a record but with a different token
        → treat as failure; do NOT retry

if result._session.token == token:
    → acquisition confirmed; no closure mutation required
    → rawData = all keys from result except "_session"
    → isNewPlayer = (rawData is empty / all keys are absent)
```

This approach relies solely on the returned record for verification. The callback has no side effects.

### 4.4 Safe callback retries

If Roblox retries the callback (write succeeded but ack was lost):
- Second call receives `current` = the already-written record (with our token)
- `current._session.jobId == JOB_ID` and `current._session.token == token` → Case B (our own lock) → writes same record again with refreshed `since` → idempotent ✅

If write truly failed (DataStore error) and retry happens:
- Second call receives `current` = original pre-write state → same logic → same result ✅

In both retry scenarios the callback's return is deterministic given `current`. No external state is involved.

### 4.5 Post-acquisition data construction

```
rawData: all keys from result excluding "_session"
─────────────────────────────────────
if rawData is empty (new player or legacy with no game fields):
    data = deepCopy(DEFAULT_DATA)
else:
    data = deepCopy(DEFAULT_DATA)
    for each k, v in rawData:
        merge v into data (preserves saved values, fills new schema keys)

sessionTokens[userId] = token
activeLocks[userId]   = true
loadedData[userId]    = data     -- _session NEVER present here
```

### 4.6 Load retries

```
for attempt = 1 to LOAD_RETRIES:
    ok, result = pcall(UpdateAsync, userId, callback)

    if not ok:
        log warning (attempt N of LOAD_RETRIES)
        if attempt < LOAD_RETRIES and player still in game:
            task.wait(LOAD_BACKOFF * attempt)
            continue
        else:
            break  → all retries exhausted → kick player

    if result._session.token == token:
        break  → success

    if result indicates another server:
        kick immediately; return nil  → do NOT retry (confirmed, not transient)

→ if all retries failed with DataStore errors:
    loadFailed[userId] = true
    kick("Your data could not be loaded. Please rejoin.")
    return nil
```

LOAD_RETRIES = 3, LOAD_BACKOFF = 2 s (backoff multiplier, so 2 s / 4 s).

## 5. Save (`savePlayer`)

### 5.1 Guards (checked before DataStore access)

```
if loadFailed[userId]       → warn; return false
if loadedData[userId] == nil → return false
if sessionTokens[userId] == nil → return false  -- session not acquired or already released
```

### 5.2 Callback logic

The callback reads the current DataStore record, verifies ownership by token, and writes updated game data while preserving the `_session` block from the authoritative DataStore record (not from memory).

```
local sessionVerified = false     -- set true inside callback if ownership confirmed
                                  -- safe: monotone false→true; identical result on retry

callback(current):
    if current == nil or current._session == nil:
        return nil   -- session record missing; abort

    if current._session.token ≠ sessionTokens[userId]:
        return nil   -- session superseded; abort

    sessionVerified = true
    newRecord = deepCopy(loadedData[userId])    -- current in-memory game data
    newRecord._session = current._session       -- session metadata from DataStore, not memory
    return newRecord
```

`sessionVerified` is a closure variable but its mutation is safe: it only transitions false → true, the condition (`token == sessionTokens[userId]`) is deterministic per `current`, and multiple callback invocations yield the same result for the same input.

### 5.3 Retry and session loss distinction

```
for attempt = 1 to SAVE_RETRIES:
    sessionVerified = false
    ok, _ = pcall(UpdateAsync, userId, callback)

    if sessionVerified:
        return true   -- confirmed write; stop retrying

    if not ok:
        log warning; backoff; continue   -- transient DataStore error → retry

    if ok and not sessionVerified:
        → callback returned nil: session ownership confirmed lost
        → loadFailed[userId] = true       -- block all future saves/cash modifications
        → warn("[DataManager] Session ownership lost for player")
        → kick player
        return false                      -- do NOT retry

→ all retries exhausted without sessionVerified:
    warn; return false
```

**Key distinction:**
- `pcall` fails → DataStore error → retry
- `pcall` succeeds, `sessionVerified = false` → confirmed session loss → do NOT retry; kick

### 5.4 `_session` preservation

The `_session` block written to the DataStore always comes from `current._session` (the DataStore record) inside the callback — never from memory. This ensures the `since` timestamp and `released` flag reflect the authoritative server state, and that a save never accidentally clears session metadata.

## 6. Refresh (`refreshSession`)

Purpose: extend `_session.since` before it reaches LOCK_TTL to prevent another server treating the lock as stale.

### 6.1 Callback

```
callback(current):
    if current == nil or current._session == nil:
        return nil   -- session gone

    if current._session.token ≠ sessionTokens[userId]:
        return nil   -- session stolen

    newRecord = deepCopy(current)
    newRecord._session.since = os.time()
    return newRecord
```

### 6.2 Failure detection

After `pcall(UpdateAsync)`:
- `pcall` fails → DataStore error; log; count consecutive failures
- `pcall` succeeds, returned record's token ≠ ours → session stolen

On session stolen (confirmed):
1. `loadFailed[userId] = true` — blocks all saves and cash modifications
2. Kick the player: "Your session was claimed by another server."
3. Remove from `activeLocks`

On consecutive DataStore errors during refresh:
- Track `lastSuccessfulRefresh[userId]` (os.time() of last confirmed refresh)
- If `os.time() - lastSuccessfulRefresh[userId] > LOCK_TTL`:
  - The lock has certainly expired; treat as stolen
  - Apply the same kick path as confirmed session loss
- Otherwise: log and continue; the lock has not yet expired

### 6.3 Refresh loop

```
task.spawn(function()
    while true do
        task.wait(LOCK_REFRESH)                 -- every 20 s
        for userId in pairs(activeLocks) do
            task.spawn(function()
                refreshSession(userId)          -- concurrent per-player
            end)
        end
    end
end)
```

## 7. Release (`releaseSession`)

Purpose: mark the session as explicitly released so the next server can acquire immediately without waiting for LOCK_TTL to expire.

### 7.1 Pre-release

Clear `sessionTokens[userId]` BEFORE the UpdateAsync call. This immediately blocks:
- Any in-flight or future `savePlayer` (guard: `sessionTokens[userId] == nil → return false`)
- Any further refresh attempts (guard: `token = sessionTokens[userId]` → nil → return)

### 7.2 Callback

```
local tokenBeforeRelease = sessionTokens[userId]  -- capture before clearing
sessionTokens[userId] = nil
activeLocks[userId]   = nil

callback(current):
    if current == nil or current._session == nil:
        return nil   -- nothing to release

    if current._session.token ≠ tokenBeforeRelease:
        return nil   -- not our session; leave it alone

    newRecord = deepCopy(current)
    newRecord._session.released = true
    return newRecord
```

### 7.3 Why clearing `sessionTokens` before the UpdateAsync is correct

If `PlayerRemoving` and `BindToClose` both reach `releaseSession` for the same player:
- Whichever runs first clears `sessionTokens[userId] = nil`
- The second call finds `sessionTokens[userId] == nil`, captures nil as `tokenBeforeRelease`, then inside the callback `current._session.token ≠ nil` → returns nil → no-op

Only one release is written to the DataStore. ✅

## 8. Disconnect and Shutdown Races

### 8.1 `PlayerRemoving`

```
PlayerRemoving:
    userId = tostring(player.UserId)
    savePlayer(player)         -- writes data, verifies token
    releaseSession(userId)     -- marks released, clears sessionTokens
    loadedData[userId]  = nil
    loadFailed[userId]  = nil
    lastRefresh[userId] = nil
```

After `loadedData[userId] = nil`, any concurrent or subsequent save attempt returns `false` immediately.

### 8.2 `BindToClose`

```
BindToClose:
    for each player in Players:GetPlayers():
        spawn:
            savePlayer(player)         -- same guard: loadFailed / loadedData / sessionTokens
            releaseSession(userId)
    
    wait up to 25 s for all spawned tasks to finish
```

### 8.3 Race analysis

**Scenario: `PlayerRemoving` and `BindToClose` for the same player run concurrently**

```
Thread A (PlayerRemoving): savePlayer → starts UpdateAsync → yields
Thread B (BindToClose task): savePlayer → starts UpdateAsync → yields
```

Both saves use `sessionTokens[userId]` (same token, not yet cleared). Both callbacks execute; both verify token match; both write identical data. Second write is idempotent — same data, same session block, same result. ✅

```
Thread A: releaseSession → captures token → clears sessionTokens[userId] = nil
Thread B: releaseSession → reads sessionTokens[userId] → nil → captures nil as tokenBeforeRelease
            → callback: current._session.token ≠ nil → return nil → no-op
```

Only one release written. ✅

```
Thread A: loadedData[userId] = nil
Thread B: savePlayer(player) [if another save starts after this] → loadedData == nil → return false
```

No save after `loadedData` is cleared. ✅

**Scenario: shutdown deadline reached while DataStore request is in flight**

Roblox terminates the server process after the BindToClose deadline (~30 s). An in-flight `UpdateAsync` may or may not complete depending on whether the HTTP layer has already sent the request. Data loss for unsaved players in this scenario is accepted and logged:

```
if deadline reached:
    warn("[DataManager] BindToClose: shutdown with N player(s) unsaved")
```

No code change prevents this; it is a platform-level constraint.

### 8.4 Duplicate save prevention summary

Duplicate saves for the same player are possible but harmless:
- Both writes carry the same token → both verify ownership → both write the same in-memory data
- Second write is idempotent

The `loadedData[userId] = nil` in `PlayerRemoving` prevents any save starting AFTER disconnect cleanup completes. The `sessionTokens[userId] = nil` in `releaseSession` prevents saves after release.

## 9. Retry and Recovery

| Operation | On DataStore error | On confirmed ownership loss | On success |
|---|---|---|---|
| `loadPlayer` | Retry up to 3×, 2 s / 4 s backoff | Kick immediately; don't retry | Build data from result |
| `savePlayer` | Retry up to 3×, 2 s / 4 s backoff | Set `loadFailed`; kick; don't retry | Return true |
| `refreshSession` | Log; track elapsed since last success | Set `loadFailed`; kick | Update `lastRefresh` |
| `releaseSession` | Single attempt, pcall'd; log errors | No-op (token mismatch in callback) | Session released |

**Never treat an unknown load result as a new player:**
- If `pcall(UpdateAsync)` fails (DataStore error), all retries exhausted: kick with `loadFailed = true`. The result of `GetAsync` / `UpdateAsync` is unknown; DO NOT fall back to `DEFAULT_DATA`.
- Only a confirmed `result._session.token == token` (meaning: we successfully acquired the session and the record is known) proceeds to data construction.

## 10. Backward Compatibility

| Concern | Handling |
|---|---|
| `TycoonPlayerData_v1` name | Unchanged |
| Player key format | Unchanged (userId as string) |
| Legacy records (no `_session`) | Treated as "available" in acquisition callback; all existing game data fields preserved verbatim |
| `_session` exposure | Never in `loadedData`; stripped before returning from `loadPlayer`; never passed to any game logic |
| `_session` in save writes | Taken from `current._session` inside callback (not from memory); game code never sees it |
| `TycoonSessionLocks_v1` | Removed; no reference anywhere in the revised design |
| Existing player progress | Merge-on-load: DEFAULT_DATA → overwrite with saved values; new keys filled with defaults, all saved values preserved |

**Legacy record first-load sequence:**
```
current = { Cash = 100, TotalEarned = 500, ... }  -- no _session
callback: no live lock (no _session field) → Case B
newRecord = { Cash = 100, TotalEarned = 500, ..., _session = {jobId, token, since, released=false} }
returned to loadPlayer
rawData = { Cash = 100, TotalEarned = 500, ... }   -- _session stripped
data = merge(DEFAULT_DATA, rawData)                 -- existing values preserved
```

No separate migration step. No data loss. ✅

## 13. Unresolved Technical Risks

**Risk 1 — `UpdateAsync` return value when callback returns nil**

If Roblox's `UpdateAsync` returns nil (rather than the existing value) when the callback returns nil, the acquisition verification `result._session.token == token` would fail with a nil-index error. The implementation must guard against `result == nil` before indexing `result._session`.

Mitigation: check `result ~= nil and result._session ~= nil and result._session.token == token`.

**Risk 2 — Roblox callback retry behavior is undocumented in detail**

The exact conditions under which Roblox retries the UpdateAsync callback are not formally documented. The design assumes retries only occur on write failure (not on read failure), that `current` is consistent within a single UpdateAsync call lifecycle, and that retries happen before `UpdateAsync` returns. If retries can happen asynchronously (after `UpdateAsync` returns) this design would need revision. No evidence of this behavior exists but it cannot be ruled out without testing.

**Risk 3 — Studio `HttpService:GenerateGUID` availability**

`HttpService:GenerateGUID(false)` requires HTTP requests to be enabled in Studio settings. If disabled, the call will error. The implementation should handle this with a pcall fallback (e.g., `os.time() .. "_" .. math.random(1e9)` as a less-unique but functional substitute in Studio).

**Risk 4 — `BindToClose` and `PlayerRemoving` ordering**

The ordering of `PlayerRemoving` vs `BindToClose` during server shutdown is not guaranteed by Roblox. The design handles both orderings safely (see §8.3), but this has not been verified in Studio. The manual test plan includes this scenario.

---

## 14. Assumptions Requiring Verification

1. `PlayerStore:UpdateAsync` returns the value written by the callback (not the pre-write value) when the callback returns non-nil.
2. `PlayerStore:UpdateAsync` returns nil (or a detectable failure indicator) when the callback returns nil, allowing ownership-loss detection from the return value alone.
3. `HttpService:GenerateGUID` is available in both Studio (with HTTP enabled) and production servers.
4. Roblox's cooperative scheduler means that clearing `sessionTokens[userId] = nil` and reading it in another coroutine cannot interleave at a sub-statement level (i.e., Lua table assignments are atomic within a single coroutine switch).
5. `Players:GetPlayers()` during BindToClose does not include players whose `PlayerRemoving` has already fired and completed.
